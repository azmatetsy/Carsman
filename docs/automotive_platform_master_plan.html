Product scope freeze

Approved functional boundaries for the initial US MVP.

Product objective

A RepairPal-style marketplace where US customers search for repair shops, receive evidence-backed preliminary repair estimates where suitable data exists, and request appointments. Shops manage profiles, quotes and bookings. Admins verify and operate the marketplace.

Launch market
United States, one metro pilot; city to be chosen
Backend
Laravel 13 (verify supported dependencies and PHP version)
Public UI
React + TypeScript + Inertia + Tailwind
Admin UI
Filament, separate /admin panel
Provider UI
Filament, separate /provider panel for MVP
Customer account
React, /account
Database
PostgreSQL + PostGIS
API
REST /api/v1, documented with OpenAPI
Infrastructure
Redis queue/cache, private object storage, CI/CD
MVP planning window
12–16 weeks with experienced team; estimate, not promise

Included in MVP

Shop directory, ZIP-radius service search, shop onboarding and admin approval, vehicle selection/VIN decoding, quote request and qualified preliminary estimates, appointment requests and shop acceptance, basic customer account, email notices, API standards, audit and QA.

Out of MVP / later

Native mobile apps, nationwide rollout, AI fault diagnosis, complex shop ERP, inventory, insurance claim workflows, advanced subscription billing, and nationwide automated estimates before data rights and accuracy are established.

Commercial data constraint: NHTSA vehicle identification does not provide reliable labor times or parts pricing. Use verified shop quotes and only publish numerical estimates supported by appropriately licensed and validated inputs.

Technology & integration architecture

One Laravel modular monolith, multiple UIs, and reusable service logic.

Logical request path

React Customer Website · Filament Admin · Filament Provider · Future Mobile & Partners
↓ ↑
Laravel Domain Services + Versioned REST API
Identity · Vehicles · Shops · Estimates · Quotes · Bookings · Notifications · Audit
↓ ↑
PostgreSQL / PostGIS · Redis · Object Storage · External Integrations

React and Filament can invoke internal Laravel application services directly; public REST APIs expose only authorized external capabilities. Do not duplicate business rules inside UI controllers.

API design contract

MethodEndpointPurpose
GET/api/v1/shopsBrowse shops by search criteria
GET/api/v1/shops/{id}Public shop detail
GET/api/v1/vehicles/makesVehicle catalog
POST/api/v1/vehicles/decode-vinVIN decoding
POST/api/v1/estimatesEstimate request/response with provenance
POST/api/v1/bookingsAppointment request
GET/api/v1/bookings/{id}Authorized booking detail
POST/api/v1/bookings/{id}/cancelCancellation with rules

API policy: versioning, OpenAPI specs, request validation, idempotency for writes, pagination, throttling, authorization, integration scopes, signed webhooks, and contract tests. Use Sanctum for first-party clients and an appropriate OAuth flow for delegated third-party access.

Primary data domains

Users & membership: users, roles, customer_profiles, shops, shop_locations, shop_members.
Vehicles & services: vehicle_makes, vehicle_models, vehicle_variants, customer_vehicles, services, shop_services.
Transactions: estimate_requests, estimate_results, source_versions, shop_quotes, bookings, booking_status_events, availability_slots.
Operations: verification_events, private_documents, reviews, notifications, audit_logs, system_settings.

Use strict business-level access checks and shop-level data isolation. Booking states: requested → confirmed → in_progress → completed, with explicit declined, cancelled, and rescheduled flows.

Quality gates and release policy

No phase is approved based on feature screenshots alone.

Standard acceptance gates

Workflow: specification → feature branch → implementation → automated CI → independent QA → approval → merge → staging → production smoke tests. No merge or production deploy without explicit approval.

Pilot launch conditions

A real US test customer can choose a vehicle and service, find a verified participating shop, request an appointment, and receive a valid shop confirmation. Admin and provider accounts are isolated, email communications work, backups have been tested, and estimate disclosures are accurate.
